## 2. 产品目标与已确认决策

### 2.1 产品目标

将已有资产管理 Demo 改造成一个能够长期真实使用的个人资产 PWA：

- 手机和电脑均可访问。
- 可安装到手机桌面，第一版不需要上架 App Store。
- 使用邮箱和密码登录。
- 第一版优先供用户本人使用，关闭公开注册，以最快、低成本完成可用成果。
- 正式资产数据保存在 Supabase 云数据库，刷新或更换设备后不丢失。
- 手机和电脑登录同一账号时读取同一份数据。
- 数据库从第一版开始按多人隔离方式设计；未来邀请更多用户时，不需要重做安全模型。
- 第一版完成后，仍可继续修改界面、字段、计算规则和录入逻辑。

### 2.2 平台选择

- **PWA 优先**：比原生 App 或微信小程序更快、成本更低，适合第一版。
- **Netlify**：负责构建和托管前端网页，不保存正式资产数据。
- **Supabase Auth**：负责邮箱账号、会话和密码恢复。
- **Supabase PostgreSQL**：保存用户资料、账户、资产和历史快照。
- **GitHub**：保存源代码和版本历史，不保存正式资产数据或秘密。
- 需要让手机在不同网络下稳定使用时，最终仍需部署 HTTPS 站点；本地地址只用于开发验收。

## 3. 第一版需求范围

### 3.1 登录与权限

- 管理员在 Supabase 手动创建第一位用户。
- 关闭公开自助注册，但保持 Email Provider 和既有用户的邮箱密码登录可用。
- 未登录时只显示登录页面，不能进入私人资产界面。
- 登录状态在刷新和重新打开页面后保持，并自动刷新会话。
- 默认退出只结束当前设备会话，不影响同一账号在其他设备的会话。
- 支持通过恢复邮件设置新密码。
- 每条业务数据绑定当前 Auth 用户 ID。
- 四张业务表开启 RLS，用户只能读写自己的记录。
- 前端只使用 Project URL 和 publishable key，不包含管理员密钥。

### 3.2 移动端界面

- 使用真实浏览器视口，不显示模拟手机外框、刘海或假状态栏。
- 适配 iPhone 安全区域、不同屏幕宽高、浏览器地址栏和虚拟键盘。
- 表单输入字号至少 16px，避免 iOS 自动缩放。
- 底部提供五个主要入口：总览、资产、记一笔、到期、我的。
- 保留深色、橙色强调的整体视觉风格。
- 手机 Safari 和微信内置浏览器最终均需人工验收。

### 3.3 账户和资产

账户字段：

- 账户名称、账户类型
- 机构名称
- 账号末四位（不得保存完整银行卡号）
- 币种
- 备注

资产字段：

- 资产名称、资产类型
- 所属账户
- 投入本金
- 当前金额
- 年化收益率
- 起息日、到期日
- 提前提醒天数
- 备注
- 创建和更新时间

字段定义：

- **投入本金**：最初投入或购买该资产的成本基准。
- **当前金额**：资产现在的价值或当前余额。
- **累计收益**：`当前金额 - 投入本金`。
- 年化收益率以百分比数值保存，例如 `3.05` 代表 `3.05%`。

必须支持：

- 新增、编辑、删除账户。
- 新增、编辑、删除资产。
- 有资产的账户不能直接删除，应先转移或删除关联资产。
- 刷新、退出再登录和更换设备后数据仍存在。
- 总资产、累计收益、账户小计和类型占比由同一份数据自动计算。
- 同名账户或同名资产不能串改，所有操作使用数据库 UUID。
- 空数据、读取中、失败、离线和重复提交有明确反馈。
- 初次使用不自动写入演示资产。

### 3.4 到期、历史和备份

- 根据到期日和提前提醒天数生成应用内提醒。
- 正确区分已到期、今天到期、近期到期和无到期日。
- 新增资产或修改本金/当前金额时生成历史快照。
- 支持 CSV 导出资产列表。
- 支持 JSON 完整备份，包含账户、资产和历史快照。
- CSV 必须防止表格公式注入。

### 3.5 PWA 与离线边界

- 提供应用名称、Manifest、192/512 图标和添加到主屏幕入口。
- Service Worker 缓存版本化静态应用外壳，但绝不缓存 Supabase Auth、数据库或其他私人 API 响应。
- 断网时可显示基础外壳和清晰离线提示；第一版不承诺离线修改及冲突合并。
- 首次冷启动未读到云端数据时，不能用 `¥0.00` 冒充真实结果。
- 发布新版本后，旧缓存不得长期阻止更新。

### 3.6 第一版暂不包含

- App Store 上架
- 微信小程序
- 公开注册、家庭共享或管理员后台
- 收费系统
- 自动连接银行
- 自动获取基金、股票或汇率行情
- 完整离线编辑与冲突同步
- 自动邮件提醒或手机推送
- 微信授权登录、Face ID/手势锁等未实际实现的功能声明
- 保存银行卡密码、网银密码、身份证号、验证码或完整银行卡号

## 4. 技术结构与数据位置

```text
手机或电脑上的 PWA
  ├─ GitHub：源代码和版本历史
  ├─ Netlify：HTTPS 前端托管与构建
  └─ Supabase
       ├─ Auth：用户、登录会话、密码恢复
       └─ PostgreSQL：profiles / accounts / assets / asset_snapshots
```

当前 Supabase 项目：

- 项目名称：`My-assest`
- Project ref：`dxxsqipdytkmcnonyjlp`
- 区域：Northeast Asia (Tokyo)

数据表：

| 表 | 用途 | 关键规则 |
|---|---|---|
| `profiles` | Auth 用户对应的个人资料 | 主键关联 `auth.users` |
| `accounts` | 资产所属的账户容器 | `owner_id` 绑定用户；有资产时禁止直接删除 |
| `assets` | 本金、当前价值、年化收益率、日期和提醒 | 金额使用 `numeric(20,2)`；复合外键阻止跨用户关联 |
| `asset_snapshots` | 资产金额历史 | 新增或金额变化自动记录；上海日历日期 |

表为空只表示尚未录入业务数据，不表示表结构或模板没有建立。

## 6. 每一步的完成标准

### 第 1 步：整理原型并确定第一版范围

- 静态 Demo 中的账户、资产、汇总和提醒不再以 DOM 文本作为数据源。
- 移除或明确标注微信授权、虚假安全状态、虚假快照数量等未实现声明。
- 明确个人首版、云端数据、PWA 路线和暂不包含项。
- 提供可操作的预览入口，并由用户确认范围。

### 第 2 步：改成真正的手机界面

- 无模拟手机外壳、刘海和假状态栏。
- 页面使用 `100dvh` 和 safe-area。
- 输入、滚动、弹窗、底栏和虚拟键盘可用。
- 不同手机尺寸无横向裁切，五个底部入口可操作。
- 用户在手机尺寸预览中确认布局。

### 第 3 步：建立云端数据库

- 可重复管理的迁移建立四张表、约束、索引和时间戳。
- 金额使用数据库精确数字类型。
- 账户、资产、快照关系及删除策略明确。
- 资产金额变化能自动产生快照。
- 云端结构检查通过并由用户确认。

### 第 4 步：增加登录和权限

- 远端 `Email Provider = enabled`，同时 `Public signup = disabled`。
- 只有管理员已创建的用户可以使用邮箱密码登录。
- 真实用户完成密码恢复、登录、刷新保持登录、退出、再次登录。
- 未登录页面不能读取或显示私人数据。
- 两用户 RLS 隔离实测通过，旧账号请求不能在切换后回写页面。
- 仓库和构建产物中没有管理员密钥或数据库密码。
- 用户明确确认第 4 步后，才能开始第 5 步。

### 第 5 步：接入真实数据并完成账户/资产操作

- 用真实账号完成账户与资产的新增、编辑、删除。
- 刷新、退出再登录后记录仍存在。
- 汇总、占比、账户小计、收益和最近记录随数据实时变化。
- 同名记录、金额边界、日期边界和账户删除限制均正确。
- 手机和电脑使用同一账号看到同一份数据。
- 失败、断网、会话过期和重复提交不会误报保存成功。

### 第 6 步：补齐 PWA 安装与离线外壳

- 生产构建包含 Manifest、图标和版本化预缓存资源。
- Supabase 私人接口不会进入 Cache Storage。
- iPhone Safari 和兼容浏览器可添加到主屏幕并独立打开。
- 首次安装、立即断网、版本更新和旧缓存清理通过验证。
- 离线冷启动不会把未加载资产显示为 0 元。

### 第 7 步：备份、导出与提醒能力

- 到期日和提醒天数计算正确，历史过期项不会遮挡近期未来项。
- JSON 备份包含账户、资产和全部快照。
- CSV 字段和编码适合常用表格软件，并防公式注入。
- 空数据和包含中文、逗号、引号等情况通过测试。

### 第 8 步：完整测试与部署验收

- 代码检查、自动测试、生产构建和敏感信息扫描通过。
- 完成 GitHub 同步门禁后，由 Netlify 构建正式站点。
- Netlify 环境变量只包含公开 Supabase 配置。
- 正式域名加入 Supabase Site URL 与 Redirect URLs。
- 手机 Safari、微信内置浏览器和电脑完成登录、CRUD、同步、导出、安装与更新验收。
- 用户确认第一版达到可长期真实使用状态。

### 7.2 已发现并修复的 Auth 配置问题

2026-08-21 只读检查远端 `/auth/v1/settings`：

```text
disable_signup = true
external.email = false
mailer_autoconfirm = false
```

当时的结论：

- 公开注册确实已关闭。
- 但 Email Provider 也被整体关闭，因此不只是 Magic Link，邮箱密码登录和密码恢复目前同样不可用。
- 用户点击 `Send magic link` 后看到 `Email logins are disabled`，根因是上述远端配置，不应只解释为“按钮点错”。
- 本地 `supabase/config.toml` 及 `test/auth-security.test.js` 当时把两个 `enable_signup` 都固定为 `false`，需要修正。

2026-08-21 已完成修复：

- 全局 `auth.enable_signup=false`：继续禁止公开自助注册。
- `auth.email.enable_signup=true`：恢复既有用户的 Email Provider。
- 远端只读复核：`disable_signup=true`、`external.email=true`。
- 无效测试邮箱自助注册返回 HTTP 422，证明公开注册仍关闭。
- 无效邮箱密码登录进入正常的凭据校验并返回 `Invalid login credentials`，不再返回 `Email logins are disabled`。
- 添加显式 `[storage.vector] enabled=false`，避免 Supabase CLI 把未使用且需付费的 Vector Storage 默认开启。

用户首次点击恢复邮件后又暴露出一次性事件竞态：SDK 已创建恢复会话并清除 URL token，但应用先读取 session、后订阅 `PASSWORD_RECOVERY`，导致页面误进资产首页。2026-08-22 已修复：

- 在创建 Supabase client 前捕获恢复 URL 意图。
- 在读取初始 session 前注册 Auth 状态监听。
- 使用两小时本地恢复标记，覆盖邮件在新标签页打开的情况。
- 新增专用 `/reset-password` 页面并加入 Supabase Redirect URLs。
- 增加“我的 → 修改登录密码”兜底：即使邮件链接误进资产首页，也能用当前有效恢复会话设置新密码。
- 更新密码成功后清理恢复 URL/标记、仅退出当前设备，并回到登录页要求使用新密码重新登录。
- 改密与登出采用分阶段错误处理：即使自动登出确认失败，也不会把已经成功的改密误报为失败；本页私人状态仍会清除并给出准确提示。
- `SIGNED_OUT` 会在初始化完成后清理残留恢复标记，避免刷新后误回设置密码页面。
- Auth 审计时间证明用户点击的恢复链接已成功建立会话；问题发生在前端页面分流，而不是邮件失效。
- 决定保留现有 UID：新建 UID 会成为不同身份，无法验证恢复流程，未来也不能自动访问旧 UID 的数据。
